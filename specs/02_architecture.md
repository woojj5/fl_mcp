# 시스템 아키텍처

## 논리 구성

```text
실험 운영자 ── 브라우저 ── 대시보드(Flask, 기본 5000)
                              ├── 학습 기록 저장소(SQLite)
                              └── 배포 모니터 ── FL 서버 및 클라이언트 상태 API

클라이언트 노드 ── 등록·모델 다운로드·업데이트 업로드 ── FL 조정 서버
       └── 로컬 데이터로 학습·예측                           └── 라운드 집계·전역 모델·예측
```

## 프로세스와 책임

| 구성 요소 | 진입점 | 기본 포트 | 책임 |
|---|---|---:|---|
| 대시보드 | `python run.py dashboard` | 5000 | 추적 데이터 조회 및 배포 모니터 |
| FL 조정 서버 | `python run.py server` 또는 `server.py` | 8080 | 클라이언트 관리, 라운드 진행, 모델·업데이트 교환 및 전역 예측 |
| FL 클라이언트 | `python run.py client` 또는 `client.py` | 8081 | 서버 등록, 로컬 학습, 업데이트 업로드, 로컬 예측 |
| 구현 라이브러리 | `fl_platform/` | 해당 없음 | Flask 대시보드, SQLite 추적 저장소, PyTorch 모델 및 HTTP 서버·클라이언트 런타임 |

## 학습 흐름

1. 서버가 모델과 전략, 최소 클라이언트 및 라운드 조건을 초기화한다.
2. 클라이언트가 서버에 자신의 ID와 접속 주소를 등록한다.
3. 클라이언트가 전역 모델을 내려받아 로컬 데이터로 학습한다.
4. 클라이언트가 학습 가중치와 메타데이터를 서버에 업로드한다.
5. 서버가 설정된 집계 전략으로 업데이트를 반영하고 다음 라운드를 진행한다.
6. 노드는 상태와 예측 API를 제공한다. 서버는 라운드 및 업데이트 지표를 SQLite에 기록하고 클라이언트의 실시간 상태는 메모리에 유지한다.

가중치는 NPZ 압축 바이트를 Base64로 인코딩해 JSON 요청으로 교환한다. HTTP 재시도는 클라이언트 자동 루프에서 수행한다. 현재 구현은 단일 서버 프로세스의 메모리 모델을 사용하므로 서버 재시작 후 라운드 상태를 복원하지 않는다.

## 통신 경계

- 대시보드에서 서버·클라이언트 URL은 선택 입력이다.
- 분산 서버·클라이언트는 HTTP API로 통신한다.
- Compose 서비스는 `fl-net` 브리지 네트워크에서 서비스 이름으로 서로 접근한다.
- 서버·클라이언트 모든 경로 중 `/health`만 공개하고 나머지는 Bearer token으로 보호한다. 대시보드는 Basic 인증을 지원한다.

## 저장소

- Compose는 `/data`를 `fl-data` named volume에 연결한다.
- 서버 SQLite 경로는 Compose에서 `/data/server_tracking.db`로 설정된다.
- 대시보드도 같은 경로를 바라보므로 서버와 추적 DB를 공유한다.
- 로컬 실행의 기본 DB 경로는 대시보드 `./tracking.db`, 서버 `./server_tracking.db`로 서로 다르다.
